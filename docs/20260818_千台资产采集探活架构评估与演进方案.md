# 千台资产采集 / 探活 架构评估与演进方案

> 日期：2026-08-18
> 场景：资产数量达到上千台时，`datasource_scrape`（数据源采集）与 `asset_probe`（资产健康探活）两条链路在现有的"串行 + 线程池 + 单进程内存冷却"模式下能否支撑？是否需要引入消息队列 / 缓存？
> 性质：~~架构评估文档（不改代码）~~ **已实施（阶段一 + 阶段二落地完成）**。实施细节见 MEMORY.md 2026-08-18 条目。<br>
> 实施状态：**阶段一（并发+批量写库+SSH限流）✅ 已完成**；**阶段二（Celery+Redis 分布式任务队列）✅ 已完成并通过端到端验证**；阶段三（Kafka/RabbitMQ）未实施，仅作预案。

---

## 0. 结论摘要（TL;DR）

1. **系统天生已经是"队列 + 缓存"架构**，只是全部是"进程内 + 内存"形态，没有显式化、可扩展、可分布式的带外中间件。
2. **上千台时的真正瓶颈不是"没有队列"，而是四件事**：
   - 采集/探活**串行或并发不足**（80s 时间预算内扫不完）；
   - **逐资产建 Session + 逐条 commit**（1k 台 ≈ 1k 次提交，DB 与 I/O 压力大）；
   - 目标机 **sshd MaxStartups 半开队列被打爆** → banner 超时（本次 `[WinError 10038]` 的根因之一）；
   - **失败冷却/熔断/结果缓存都在单个进程内存里**（`_scrape_fail_cache`），多进程/多机时完全失效、重复扫同一台。
3. **建议：先做纯代码优化（零新依赖）即可解决 80% 瓶颈；二阶段才引入 Celery + Redis；Kafka/RabbitMQ 为最终可选项，非当前所需。**
4. **不建议一开始就上 Kafka / RabbitMQ**：对单体 FastAPI + PostgreSQL 的规模是过度设计，引入的运维复杂度（broker 集群、分区、重放、审计）远超收益。

## 2. 上千台的瓶颈逐项评估

### 2.1 并发模型：串行 / 低并发是首要瓶颈

- **数据源采集是串行的**。上千个源，即便每个只耗 1-2s，80s 预算只能覆盖几十个，其余全部 skip。
- **资产探活只有 10 并发**。上千台按 5s 超时算，10 并发一轮约 500+s，远超任何合理巡检周期。

> 结论：**并发是瓶颈起点**。只有先提升并发（有界高并发 + 队列化分片），后面谈 DB 批处理、分布式才有意义。

### 2.2 DB 写入：逐条 commit 是隐性瓶颈

- 上千台探活 = 上千次 `commit()` + 上千次 `svc_up` 指标写入 + 上千次 Session 创建/销毁。
- Postgres 下虽然比 SQLite 好，但无谓的往返消耗也会拖慢。

> 结论：**应改为批量 upsert / 合并提交 + 复用一个只读快照与一个写批次**。

### 2.3 目标机侧：sshd 半开队列（`MaxStartups`）

- 高频并发 SSH 会让目标机 sshd 排队，banner 读取超时 → 本次 `[WinError 10038]` 的诱因之一。
- 项目已有对策（低频 `_ssh_interval` + 失败降级 TCP），但只是"单源层面"的节流，没有"全局限流"。

> 结论：**需要全局 SSH 信号量限流**（同时最多 N 个在建 SSH 连接），从源头避免半开队列被打爆。

### 2.4 状态共享：进程内缓存是扩展性硬伤

- `_scrape_fail_cache`（熔断）、失败冷却、低频窗口判断都在**单进程内存**。
- 一旦拆成多 worker / 多机，各进程状态不一致 → 同一台被重复扫、熔断失效。

> 结论：**这正是"缓存"真正要落地的点** —— 把冷却/熔断/节流状态放到共享存储（Redis）而非进程内存。

### 2.5 可靠性 / 可观测

- 任务失败、重试、耗时的任务级日志依赖 `startup._run_bg_service` 的宽泛日志。
- 上千台时缺少"每台每次探测结果"的可追踪队列语义（当前结果是边扫边落库）。

## 3. 演进方案（分三阶段，由轻到重）

> 原则：**能不加中间件就不加**；每阶段都有独立的、可验证的收益；每阶段都保留现有调用方语义。

### 阶段一：纯代码优化（零新依赖，建议立即做）

目标：解决 80% 瓶颈，不引入任何中间件，可在现网直接验证。

| 举措 | 说明 | 收益 |
|---|---|---|
| 数据源采集改**有界高并发** | `scrape_all_sources` 由串行改为 `ThreadPoolExecutor(max_workers=N)` + 并发上限，替代 80s 硬预算的粗暴 skip；仍复用失败冷却 | 上千源当轮覆盖率大幅提升 |
| 资产探活并发 10 → 50~100 | 受控提高并发 | 高频巡检周期显著缩短 |
| **全局 SSH 信号量限流** | 全局 `Semaphore(M)`，所有 SSH 在建连接统一限流，避免打爆 sshd 半开队列 | 从根上减少 banner 超时 / `10038` |
| **批量写库** | 探活结果批量 upsert + 合并 `svc_up` 提交，替代逐条 commit | DB 往返次数 ↓ 1~2 个数量级 |
| 失败冷却/低频窗口保留并微调 | 维持进程内缓存 + 可控参数化 | 兼容现网，不破坏语义 |

**验证方式**：模拟 1000+ 资产（或批量造真实资产），对比改造前后 `datasource_scrape` 完成时间、资产探活一轮耗时、DB 每秒 commit 次数。

**成本**：仅改动 `datasource_service.py` / `asset_service.py` / `ssh_helper.py`，无新依赖。

> 阶段一做完，若无脑上 MQ 的冲动，先观察：**单进程 + 高并发 + 批量写库通常已能顶住上千台**。

### 阶段二：引入 Celery + Redis（分布式任务 + 共享缓存）

触发条件：多 worker / 多机部署，或阶段一并发仍不够、需要独占进程跑采集。

| 组件 | 用途 |
|---|---|
| **Celery** | 后台任务队列（producer 定时投递任务，worker 并行消费），替代 `ThreadPoolExecutor` 与 `startup` 线程池的角色；支持定时调度（beat） |
| **Redis** | ① Celery broker / result backend；② **分布式失败冷却 + 节流 + 低频窗口状态**（替代 `_scrape_fail_cache` 等进程内内存）；③ 结果缓存 |

**收益**
- 采集/探活**跨进程、跨机器分片**，worker 可水平扩容；
- **熔断 / 冷却 / 节流全局一致**，多 worker 不重复扫同一资产；
- Redis 缓存让"最近 N 次探测结果 / 正在进行的探测"可被 API 层直接读取，减轻 DB 查询压力。

**代价**：需部署 Redis；`_scrape_fail_cache` 等迁移为 Redis key；引入 Celery worker 进程与运维（supervisor/systemd 常驻）。这是"性价比最高的转折点"。

**选型理由（对比）**
- 选 Celery 而非直接上 Kafka：Celery 任务粒度贴合"每资产一次探测/采集"的自然模型，重试/队列/调度开箱即用，比手搓 broker 简单可靠。
- 需要 Redis 是因为它同时胜任 broker / 缓存 / 熔断三职，一份依赖多处复用。

### 阶段三（可选，触发才做）：Kafka / RabbitMQ

触发条件：达到**几千台以上、多地域、需要消息持久化 / 重放 / 审计 / 精确一次投递**的金融级场景，或采集与消费严重解耦（如采集 → 告警 → 入库 → 训练多级流水线）。

| 特点 | 说明 |
|---|---|
| 持久化 & 重放 | 采集结果 / 事件可落盘、断点续传 |
| 高吞吐削峰 | 大规模事件流稳定吞吐 |
| 解耦 | producer（采集）与 consumer（入库/训练/告警）彻底分离 |

**代价**：最重，需维持 broker 集群；仅当前规模不应引入。

## 4. 阶段对比小结

| 维度 | 阶段一（纯代码） | 阶段二（Celery+Redis） | 阶段三（Kafka/RabbitMQ） |
|---|---|---|---|
| 新依赖 | 无 | Redis | Kafka/RabbitMQ 集群 |
| 并发提升 | 有界高并发 | 多 worker/多机 | 高吞吐事件流 |
| 冷却/熔断共享 | 否（进程内） | 是（Redis） | 是（+持久化） |
| 可水平扩容 | 弱 | 中 | 强 |
| 运维成本 | 零 | 中 | 高 |
| 适合规模 | ~1k 台 | 1k~数千台 / 多机 | 数千台+ / 多地域 / 审计 |

## 5. 推荐实施顺序

1. **现在**：跑通阶段一（纯代码优化），用千台资产压测出真实瓶颈数据。
2. **若满足**（单机并发已够）：阶段一即可，维护低成本。
3. **若不满足 / 需多 worker / 多机**：上阶段二（Celery + Redis），把冷却/节流迁到 Redis。
4. **仅当**出现持久化/重放/审计/大规模事件流需求时：评估阶段三。

> **建议守住一条底线：当前规模不引入 Kafka/RabbitMQ。** 先榨干阶段一的性价比，再按真实压测数据决定是否走到阶段二。

### 落地开关与环境区分（2026-08-18 决定）

- **开发/本地环境**：`AIOPS_CELERY_ENABLED=false`（默认），采集/探活走**进程内后台服务**，无需起 worker/beat，最简单。（已写进 `.env`）
- **生产环境**：将 `AIOPS_CELERY_ENABLED=true`，并拉起 `_start_celery_worker.bat` + `_start_celery_beat.bat`（或 systemd/supervisor 常驻），方可为上千台资产提供多 worker/多机横向扩展。
- 分布式路径始终带降级：Redis 不可达时自动回退进程内，不中断业务。

## 6. 附：本次 `[WinError 10038]` 与千台架构的关联

- 单台 banner 超时是表象；根因方向包括：目标机 sshd `MaxStartups` 半开队列被打爆（高并发 SSH）、banner 读取超时后 paramiko Transport 线程在已关闭 socket 上 recv。
- 已在 `ssh_helper.py` 修复：`_close_quietly()`（先 `stop_thread` 再 close）+ banner 快速失败（`_MAX_BANNER_RETRY=2`）+ banner_timeout 15s→8s。
- **千台架构层面**：阶段一的"全局 SSH 信号量限流 + 低频窗口全局化"能从根上避免再次触发半开队列搬出，是防止 `10038` 群体性复发的重要配套。
