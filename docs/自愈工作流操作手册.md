# 自愈工作流操作手册

> 本文档说明如何配置、测试和使用自愈工作流，实现多步骤故障自动处置。

---

## 一、什么是自愈工作流

自愈工作流是**多步骤修复流程编排引擎**。与单动作的简单自愈规则不同，工作流支持将多个修复动作按顺序执行，形成完整的自愈闭环。

**典型场景：**

```
CPU 告警触发 → 健康检查 → 重启服务 → 再次健康检查 → 通知
```

**触发方式（3种）：**

| 方式 | 说明 | 适用场景 |
|------|------|---------|
| 自动触发 | 工作流关联告警规则 ID → 告警触发时自动匹配 → 生成 PendingAction 待审批 → 审批后执行 | 生产环境常态化自愈 |
| AI 推荐 | 自愈 AI 分析时看到所有启用的工作流 → 认为匹配则推荐 → 人工审批 → 执行 | AI 辅助决策阶段 |
| 手动运行 | 在「自愈工作流」页面点击「运行」→ 对当前触发告警执行 | 测试/临时处置 |

## 二、创建第一个工作流

### 场景：CPU 使用率过高自愈

**目标：** 当 CPU 告警触发时，自动执行 `healthcheck → restart → healthcheck → notify`

**操作步骤：**

1. **进入菜单**：左侧导航 → 运维自愈 → 自愈工作流
2. **点击「+ 新建工作流」**
3. **填写信息：**
   - 名称：`CPU 高自愈流程`
   - 关联告警规则 ID：输入告警规则 ID（如 `1`，可在「告警规则」页面查看）
   - 留空则：AI 推荐时仍可见，但不会自动触发（需手动或 AI 推荐）
4. **编排步骤：**
   - 点击「+ 健康检查」→ 添加第一步
   - 点击「+ 重启」→ 添加第二步
   - 点击「+ 健康检查」→ 添加第三步
   - 点击「+ 通知」→ 填写通知内容 `CPU 自愈完成`
   - 拖拽排序：↑↓ 按钮调整步骤顺序
5. **点击「保存」**

### 场景：磁盘空间不足自愈

**步骤编排：** `healthcheck → clean → healthcheck → notify`

| 步骤 | 动作 | 参数 |
|------|------|------|
| 1 | healthcheck | 无 |
| 2 | clean | （可选）路径：`/var/log` |
| 3 | healthcheck | 无 |
| 4 | notify | 消息：`磁盘清理完成` |

## 三、可用动作一览

| 动作 | 说明 | SSH 通道 | K8s 通道 | Docker 通道 |
|------|------|---------|---------|-----------|
| **healthcheck** | 健康检查 | `systemctl is-active` / `uptime` | `kubectl rollout status` / `kubectl get pod` | `docker exec echo` |
| **restart** | 重启 | `systemctl restart` | rollout restart / delete pod | `docker restart` |
| **clean** | 清理文件 | `find -delete`（限 /tmp /var/log /var/cache /opt /home） | ❌ | ❌ |
| **scale** | 扩缩容 | ❌ | `kubectl scale` | ❌ |
| **notify** | 通知 | 记录日志（通知链路待集成） | 记录日志 | 记录日志 |
| **run_command** | 执行命令 | 全量命令（危险黑名单拦截） | 仅放行只读命令 | 仅放行只读命令 |

**安全机制：**
- 变更操作（restart/clean/scale）→ 必须人工审批 → 生成 PendingAction → 确认后执行
- 只读操作（healthcheck/run_command 只读）→ 自动执行，无需审批
- 危险命令黑名单拦截（rm -rf /、mkfs、dd、shutdown 等）
- 建议创建后先点「模拟」再点「运行」

## 四、测试工作流

### 4.1 模拟运行（推荐方式）

1. 在工作流列表中找到刚创建的工作流
2. 点击「🔍 模拟」按钮
3. 系统会**模拟执行**所有步骤，显示每步的预期结果
4. 确认无误后再点击「运行」

**模拟结果弹窗示例：**

```
✅ 通过 | 告警 #1 · 步骤 1: healthcheck | 39.106.16.32
  → [模拟] 步骤 1: healthcheck {} (dry-run)
✅ 通过 | 告警 #1 · 步骤 2: restart | 39.106.16.32
  → [模拟] 步骤 2: restart {} (dry-run)
✅ 通过 | 告警 #1 · 步骤 3: healthcheck | 39.106.16.32
  → [模拟] 步骤 3: healthcheck {} (dry-run)
✅ 通过 | 告警 #1 · 步骤 4: notify | 39.106.16.32
  → [模拟] 步骤 4: notify {} (dry-run)
```

### 4.2 实际运行

1. 确认有「触发中」的告警（可在「告警列表」页面查看）
2. 点击「运行」按钮
3. 系统会找到最近 3 条触发中的告警，依次执行所有步骤
4. 执行结果写入自愈日志，可在页面下方查看

### 4.3 查看执行日志

工作流页面下方「自愈日志」表格显示：
- 时间线（按执行时间倒序）
- 工作流 ID + 类型标记（工作流/规则）
- 执行的每个动作
- 目标资产
- 成功/失败状态

## 五、自动触发配置

### 5.1 告警规则 → 工作流关联

1. 进入「告警规则」页面，创建或编辑一条告警规则
2. 记录该规则的 ID（从 URL 或列表查看）
3. 进入「自愈工作流」页面
4. 创建或编辑工作流，在「关联告警规则 ID」字段填入该 ID
5. 保存后，该告警规则触发的告警会自动匹配此工作流

**流程：**

```
告警触发 → check_and_remediate 后台轮询
  → 匹配 rule_id 找到 AutoRemediation（单动作规则）？→ 生成 PendingAction
  → 无匹配规则？→ 匹配 rule_id 找到 RemediationWorkflow？→ 生成 PendingAction(action_type=workflow)
  → 都无匹配？→ 走 AI 分析路径
```

### 5.2 同一规则可关联多个工作流？

当前设计：**一条告警规则只能关联一个工作流**（rule_id 唯一匹配）。如果需要多方案，可以：
- 规则路径：1 条 AutoRemediation（单动作）+ 1 个 RemediationWorkflow（多步骤）→ 两者都会生成 PendingAction
- AI 路径：AI 看到所有启用的工作流，选择最匹配的推荐

## 六、编辑与维护

### 编辑工作流

1. 在工作流列表中找到目标工作流
2. 点击「编辑」按钮
3. 修改名称、关联规则 ID、步骤序列
4. 点击「保存」

### 启用/禁用

- 点击「禁用」→ 工作流停止匹配，不再生成 PendingAction
- 点击「启用」→ 恢复匹配

### 删除

- 点击「删除」→ 确认后永久删除
- 已生成的 PendingAction 不受影响（仍可审批执行）

## 七、常见问题

### Q1: 工作流创建了但不触发？

检查：
1. 工作流是否已「启用」（卡片上显示绿色「启用」徽章）
2. 告警规则 ID 是否匹配（工作流卡片显示 `规则 #1`）
3. 是否有触发中的告警（`alert.status == "triggered"`）
4. 当天是否已有同告警的 PendingAction（去重机制，每天每个告警最多 1 条）

### Q2: 模拟通过但实际运行失败？

可能原因：
- 资产 SSH 连接不可达（检查资产状态和连接配置）
- 资产 ci_type 与动作不匹配（如 scale 动作但资产不是 K8s 类型）
- 危险命令被黑名单拦截

**排查：** 查看自愈日志中的失败输出，或直接 SSH 到目标资产手动测试。

### Q3: AI 推荐的工作流不匹配？

AI 推荐的是所有启用的工作流。如果 AI 总推荐错误的工作流：
1. 给工作流命更清晰的名称（如 `CPU 高自愈` 而非 `流程1`）
2. 关联正确的 rule_id，让自动触发路径优先于 AI 推荐
3. 禁用不相关的工作流，减少 AI 的候选列表

### Q4: 如何给工作流添加服务名参数？

在 healthcheck/restart 步骤中，可以填写「服务名」参数。例如：
- restart 步骤填 `nginx` → 执行 `systemctl restart nginx`
- healthcheck 步骤填 `nginx` → 执行 `systemctl is-active nginx`

如果留空，healthcheck 默认执行 `uptime`（只检查主机存活），restart 需从 params 取 `service` 值。

## 八、推荐模板

### 模板 1：CPU 高自愈

```
名称: CPU 高自愈
关联规则: cpu_usage 告警规则 ID
步骤:
  1. healthcheck              → 检查当前状态
  2. restart  (服务: nginx)    → 重启服务
  3. healthcheck              → 确认恢复
  4. notify (消息: CPU 自愈完成) → 通知
```

### 模板 2：磁盘满自愈

```
名称: 磁盘清理自愈
关联规则: disk_usage 告警规则 ID
步骤:
  1. healthcheck              → 检查主机存活
  2. clean  (路径: /var/log)   → 清理旧日志
  3. healthcheck              → 确认磁盘恢复
  4. notify (消息: 磁盘清理完成) → 通知
```

### 模板 3：K8s Pod 异常恢复

```
名称: K8s Pod 异常恢复
关联规则: k8s_pod_crash 告警规则 ID
步骤:
  1. healthcheck              → 检查 Pod 状态
  2. restart                  → 重启 Pod（K8s: delete pod / rollout restart）
  3. healthcheck              → 确认 Pod 恢复
  4. notify (消息: Pod 已恢复)  → 通知
```

---

> **专业名词：** **Playbook Engine**（剧本引擎）— 自愈工作流本质是一个运维剧本引擎，支持多步骤编排、条件分支、回滚策略、审批闸门。当前实现支持线性步骤执行 + 失败即停 + 只读/变更自动审批分派，后续可扩展条件分支和重试策略。
