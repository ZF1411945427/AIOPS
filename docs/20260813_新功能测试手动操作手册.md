## 2026-08-13: 智能体编排告警自动触发 + 并行 fan-out(B1/B2/B4)

> 对应任务: 赶超计划 B1(告警自动触发)/ B2(并行 fan-out)/ B4(重启续跑)。

### 功能说明

- **B1 告警自动触发**: 工作流 `trigger_type=alert_auto` 且 `enabled=true` 时, 后端 `background_loop` 每轮(约 30s)轮询最近 10 分钟新告警, 按 `trigger_condition`(如 `{"severity":"critical"}`)匹配后自动拉起工作流, 同一告警对同一工作流只触发一次。
- **B2 并行 fan-out**: 工作流执行时, 每轮取所有"依赖已满足"的 pending 节点**并发执行**(不是串行), 并发上限 `workflow_max_concurrency`(默认 4, 可配)。
- **B4 重启续跑**: 后端启动时扫描 `running`/`awaiting_confirm` 的 run 自动续跑。

### 操作步骤

#### 1. 准备: 确认预置告警触发工作流

1. 登录系统 → 左侧菜单 **AI运营者 → Agent 管理 → 智能体编排**。
2. 确认列表中「智能告警根因分析」「故障自愈决策」两条工作流的 `trigger_type` 为 `alert_auto`(未修改则默认如此)。
3. (可选)编辑「故障自愈决策」, 在节点画布上确认有「查询告警 → 决策分析 → 条件分支 → 自愈/升级/通知」结构。

#### 2. 制造一条符合条件的新告警

- **方式A(推荐, 界面造)**: 左侧 **监控告警 → 告警规则** 新建/启用一条规则(如 `metric_name=cpu_usage`, `condition=>`, `threshold=90`, `severity=critical`), 然后到 **监控告警 → 告警** 查看是否自动产生。
- **方式B(若规则不出告警, 用后台直接插告警, 需在本机执行)**:
  ```powershell
  python -c "import sys; sys.path.insert(0,'.'); from app.database import get_session_for,get_db_mode; from app.models import Alert,AlertRule; db=get_session_for(get_db_mode())(); r=AlertRule(name='manual-test',metric_name='cpu_usage',condition='>',threshold=90,severity='critical',enabled=True); db.add(r); db.commit(); db.add(Alert(rule_id=r.id,asset_id=1,metric_name='cpu_usage',actual_value=99,threshold=90,severity='critical',status='triggered',message='manual trigger')); db.commit(); print('alert ok, rule',r.id); db.close()"
  ```

#### 3. 验证告警自动触发工作流

1. 造好告警后**等待 30~60s**(后台轮询周期)。
2. 打开 **AI运营者 → Agent 管理 → 智能体编排**, 切换到「工作流执行记录」(或访问 `AgentWorkflowRunsView` 页面)。
3. 预期: 出现一条新 run, `trigger_source=alert`、`triggered_by=system`, 对应工作流是「智能告警根因分析」或「故障自愈决策」; 状态最终为 `completed`。
4. 点开该 run 看节点执行详情, 确认节点全部有输出(告警查询 → 知识库 → LLM 结论)。
5. 防重复验证: 同一告警 id 不应产生第二条 run(再次等待一个轮询周期, run 数量不增)。

#### 4. 条件过滤验证(可选)

- 若「故障自愈决策」`trigger_condition` 为 `{"severity":"critical"}`, 则插入一条 `severity=warning` 的告警, 等待一个周期后确认**不会**触发该工作流。

#### 5. 并行 fan-out 验证

1. 在 **智能体编排** 新建一个工作流: 一个 start 节点 → 3 个并行分支节点(任意类型, 如 code/http)→ 汇聚到 end 节点。
   - code 节点示例(注意沙箱禁 import): `result = {'task': inputs.get('name')}`, `inputs_mapping` 填 `{"name": "'分支A'"}`。
2. 手动执行该工作流。
3. 预期: 各分支节点 `started_at` 时间接近(并行), 全部 `completed`, run 状态 `completed`。
4. (进阶)把 3 个分支换成指向本地慢接口的 http 节点(各 sleep 1.5s), 串行需 ~4.5s, 并行 ~1.5s, 观测执行耗时明显缩短。

#### 6. 重启续跑验证(可选)

1. 执行一个含 LLM 节点的工作流(耗时较长), 执行中途 `Ctrl+C` 停后端。
2. 重启后端(`python run.py`)。
3. 查看日志 `[workflow-resume] 恢复 N 个未完成工作流 run`, 以及 run 状态续跑至完成。

### 通过标准

- [ ] 告警产生后 1 分钟内自动拉起对应工作流 run(trigger_source=alert)
- [ ] 同一告警不重复触发
- [ ] `severity=warning` 不触发 `severity=critical` 条件工作流
- [ ] 多分支工作流并发执行, run 状态 completed
- [ ] 重启后端后未完成 run 可续跑

## 2026-08-13: Agent 工具装饰器链 + 工具级超时(A1/A2)

> 对应任务: 赶超计划 A1(工具级超时)/ A2(装饰器横切链)。

### 功能说明

- **A1 工具级超时**: 所有 MCP 工具调用默认 30s 超时(可在工具定义里用 `timeout_seconds` 覆盖, 如 `query_metrics`=10s、`query_knowledge_rag`=45s), 超时返回 `{"status":"error","timeout":true}`, Agent 不卡死。
- **A2 装饰器链**: 工具可声明 `ratelimit_per_minute`(限流)/ `audit_enabled`(审计)/ `review_gate`(审查门); `propose_action` 已开启审计+审查门, `query_metrics` 已开启限流。

### 操作步骤

#### 1. 查看工具元数据(能力中心)

1. 左侧 **AI运营者 → Agent 管理 → Agent 能力中心**。
2. 预期: 工具列表字段包含 `timeout_seconds` / `ratelimit_per_minute` / `audit_enabled` / `review_gate`(后端 `/agent/api/capabilities` 返回)。
3. 确认 `query_metrics` 显示 timeout=10s, `propose_action` 显示 audit=true / review_gate=true。

#### 2. 工具超时验证

- 方式A(界面): 在 **AI运营者 → AI助手 → 智能助手** 对话中, 让 Agent 调用一个会卡住的工具(若无现成慢工具, 用方式B验证)。
- 方式B(后台直接调, 需本机执行):
  ```powershell
  python -c "import sys,time; sys.path.insert(0,'.'); from app.services.mcp_registry import register_mcp_tool, call_mcp_tool
  @register_mcp_tool(name='__slow_t', description='slow', timeout_seconds=1)
  def f(db=None,user_id=None,**k): time.sleep(5); return {'ok':1}
  r=call_mcp_tool('__slow_t',{}); print(r)"
  ```
  预期: 约 1s 后返回 `timeout: true` 错误, 而非卡 5s。

#### 3. 限流验证

- 后台执行(每分钟最多 2 次示例):
  ```powershell
  python -c "import sys; sys.path.insert(0,'.'); from app.services.mcp_registry import register_mcp_tool, call_mcp_tool
  @register_mcp_tool(name='__rl_t', description='rl', ratelimit_per_minute=2)
  def f(db=None,user_id=None,**k): return {'ok':1}
  for i in range(3): print(i, call_mcp_tool('__rl_t',{})['status'])"
  ```
  预期: 第 3 次返回 `error`(触发限流)。

#### 4. 工具审计验证

1. 在 **智能助手** 对话中发起一个运维操作提议(Agent 调用 `propose_action`, 出现"待确认动作")。
2. 后台查审计日志表:
   ```powershell
   python -c "import sys; sys.path.insert(0,'.'); from app.database import get_session_for,get_db_mode; from app.models import AuditLog; db=get_session_for(get_db_mode())(); 
   for l in db.query(AuditLog).filter(AuditLog.action=='tool_execute').order_by(AuditLog.id.desc()).limit(3): print(l.target_id, l.path, (l.request_body or '')[:40]); db.close()"
   ```
3. 预期: 出现 `target_id=propose_action`、`path=tool://propose_action`、`action=tool_execute` 的审计记录。

### 通过标准

- [ ] 能力中心 API 返回装饰器元数据字段
- [ ] 超时工具在设定时间内返回 timeout 错误
- [ ] 超限后工具返回限流错误
- [ ] `propose_action` 调用落 AuditLog

## 2026-08-13: A4 Reviewer 写操作审查门

### 功能说明
- 高危/写操作（`execute_*` 且 `review_gate=True` 或风险等级 high/critical）在用户确认后执行前，先经过 LLM reviewer 子代理二签，`reject` 则阻断执行并落审计。

### 操作步骤

#### 1. 待确认动作触发审查
1. 入口: **AI运营者 → AI助手 → 智能助手**。
2. 让 Agent 调用 `propose_action` 提议一个高危操作（如重启服务/执行命令），出现"待确认动作"卡片。
3. 点击 **确认执行**。
4. 预期: 若 LLM 判定操作有风险（资产未验证/生产写操作），动作状态变为 `failed`，卡片显示"审查未通过"+ 拒审理由（reviewer 判词）；若判定安全则正常执行。

#### 2. 查看审查结论落库
1. 后台查 `pending_actions.review_result` 字段（JSON: verdict/confidence/reason/suggestions）:
   ```powershell
   python -c "import sys; sys.path.insert(0,'.'); from app.database import get_session_for,get_db_mode; from app.models import PendingAction; db=get_session_for(get_db_mode())();
   for a in db.query(PendingAction).filter(PendingAction.review_result!='').order_by(PendingAction.id.desc()).limit(3): print(a.id, a.action_type, (a.review_result or '')[:120]); db.close()"
   ```
2. 预期: 高危动作的 `review_result` 非空，且含 `verdict` 字段。

#### 3. 工作流节点审查
1. 入口: **工作流 → 新建/编辑**，配置一个高危 tool 节点（如 `execute_run_command`）。
2. 运行工作流，节点等待确认后点击确认。
3. 预期: 与步骤 1 相同——高危节点先过 reviewer，`reject` 则节点标记 `failed`、工作流继续推进（`_advance_run`）。

#### 4. 低危操作不过审
1. 确认一个低风险动作（如 `acknowledge_alert`）。
2. 预期: 直接执行成功，`review_result` 为空（未被审查）。

### 通过标准
- [ ] 高危写操作确认后先触发 LLM reviewer 二签
- [ ] reviewer 判定 reject 时动作被阻断（status=failed）且展示理由
- [ ] `pending_actions.review_result` 落库审查 JSON
- [ ] 低危/只读操作不经过审查门
- [ ] 工作流高危节点确认同样走审查门

## 2026-08-13: B3 工作流 cron 定时调度

### 功能说明
- `trigger_type=cron` 的智能体工作流按 cron 表达式（5 字段）定时自动触发，`trigger_condition={"cron":"0 8 * * *"}`；分钟级精度，后台每轮询周期检查一次，同分钟防重复。

### 操作步骤

#### 1. 配置 cron 触发器
1. 入口: **智能体工作流 → 新建/打开工作流 → 顶部「⏰ 触发器」**。
2. 触发类型选 `cron（定时调度）`，填写 cron 表达式（如 `*/2 * * * *` = 每 2 分钟）。
3. 点「保存」，打开「未来执行计划」确认 next run 时间正确。
4. 后台验证: `GET /agent-workflow/api/workflows/{id}` 返回 `trigger_type="cron"`、`trigger_condition={"cron":"*/2 * * * *"}`。

#### 2. 定时自动触发
1. 等 2 分钟（或把 cron 设为命中当前分钟）。
2. 预期: **工作流执行记录**出现新 run，`trigger_source="cron"`、`triggered_by="system"`。
3. 防重复: 同一分钟内反复点「触发」或重启后台，不产生第二个 run。

#### 3. 未来执行计划预览
1. 后台: `POST /agent-workflow/api/cron/preview` body `{"cron":"*/30 * * * *"}`。
2. 预期: 返回未来 5 次执行时间（`2026-08-13 21:00, 21:30, ...`）。
3. `GET /agent-workflow/api/cron/next-runs` 返回所有启用 cron 工作流的 next run。

### 通过标准
- [ ] 前端可配置 cron 触发器并保存 `trigger_condition={"cron":...}`
- [ ] cron 命中时自动拉起工作流（trigger_source=cron）
- [ ] 同一分钟不重复触发
- [ ] 非法 cron 表达式不崩溃（跳过+告警日志）
- [ ] preview / next-runs API 返回正确计划

## 2026-08-13: B5 notify / agent 工作流节点

### 功能说明
- `notify` 节点：通过 NotificationChannel（飞书/钉钉/企微 webhook）发送通知，内容支持 `{{ }}` 模板引用上游节点输出。
- `agent` 节点：把子代理（persona）嵌入工作流——指定子代理名或自动路由，prompt 模板渲染后调 LLM 生成专业回复。

### 操作步骤

#### 1. 新建 notify 节点
1. 入口: **智能体工作流 → 新建**，从左侧拖入 **「IM 通知」** 节点。
2. 配置: 渠道名（NotificationChannel.name，需先在 IM 集成里配置）、标题、内容（可写 `{{ nodes.xxx.output.data }}` 引用上游）。
3. 保存运行; 预期: 节点完成，对应 IM 群收到通知；渠道不存在/未配置 webhook 时节点失败并显示原因。

#### 2. 新建 agent 节点
1. 拖入 **「子代理」** 节点。
2. 配置: 子代理（选具体专家或留空自动路由）、任务文本（支持模板）。
3. 运行; 预期: 节点返回 `reply`（子代理 LLM 专业回复），`sub_agent` 字段显示实际路由的子代理名。

#### 3. 组合编排
- 典型剧本: 告警触发 → agent 分析 → notify 通知 → 结束。验证 start→agent→notify→end 全链路状态与输出传递。

### 通过标准
- [ ] notify 节点渠道不存在/未配置 webhook 时正确失败（不崩溃）
- [ ] notify 内容模板渲染正确
- [ ] agent 节点自动路由到正确子代理并返回 reply
- [ ] 组合工作流全链路执行、节点间输出传递正常
- [ ] 工作流执行记录显示节点级状态与错误原因

- [ ] 报告为结构化 JSON(summary/root_causes/evidence/recommendations/risks),Markdown 可读
- [ ] 无 LLM Provider 时不产生空壳报告(降级为算法包结论)
- [ ] 同一故障单不重复调查(去重)
- [ ] 报告自动回写聊天会话;双向 IM 渠道收到推送
- [ ] `GET /incidents/api/reports/investigation` 列表与详情 API 正常

## 2026-08-13: 凭据保险库 Secrets Vault(F3)

### 功能说明
- 集中加密存储连接凭据(密码/Token/API Key/私钥),数据库只存 Fernet 密文不存明文;连接配置只存 `{{secret:name}}` 引用,运行时自动解密注入;带引用解析测试与失效引用扫描。

### 操作步骤
1. 入口: 系统配置 → 系统管理 → **凭据保险库**(`/secret-vault`)
2. 新建凭据: 点击「+ 新建凭据」→ 填引用名(如 `prod_db_password`)、类型(密码)、作用域、描述、值 → 保存
3. 确认列表: 值列只显示 `••••••••` 与「已设置」;重复创建同名 → 提示「凭据名称已存在」
4. 编辑: 修改描述保存;新值留空 → 原值不变(空值=不更新)
5. 引用解析测试: 在「🧪 引用解析测试」输入 `{"ssh_password":"{{secret:prod_db_password}}"}` → 解析 → 显示真实值;输入不存在的引用名 → 原样保留(不报错)
6. 复制引用: 点击列表里的 📋 复制 `{{secret:prod_db_password}}`
7. 数据源引用: 在数据源管理(SSH/K8s)的敏感字段填 `{{secret:prod_db_password}}` 而非明文 → 保存 → 本页「📎 数据源引用一览」出现该引用且状态「✓ 有效」
8. 删除凭据: 删除后引用一览该条变「✗ 失效(保险库无此凭据)」

### 通过标准
- [ ] 列表/详情/编辑全程不回显明文,只显示 `***` + `has_value`
- [ ] 数据库 `secret_vaults.secret_value_encrypted` 为密文,检索不到明文值
- [ ] 引用解析正确替换;未匹配引用 fail-open 原样保留
- [ ] 数据源使用 `{{secret:name}}` 引用可正常「测试连接」(密码已解密注入),测试失败信息不泄露密钥
- [ ] 空值=不更新;重名创建被拦截;删除后引用扫描显示失效
- [ ] 菜单「凭据保险库」admin 可见可操作;`npm run build` 通过

## 2026-08-13: K8s 多集群 data plane + Edge 升级协作器(F5)

### 功能说明
- 多集群注册表：把多个 K8s DataSource 聚合为命名集群，controller/node 双角色，每集群独立 telemetry 通道（事件/资产汇总隔离）。
- Edge 升级任务：状态机(pending/running/completed/failed/rolled_back) + 批次滚动 + 逐 agent upgrade→verify，失败自动回滚，全程落库持久化。

### 操作步骤
1. 入口: 系统配置 → 系统管理 → **多集群管理**(`/multicluster`) / **Edge 升级**(`/upgrade-jobs`)
2. 注册集群: 「+ 注册集群」填集群名/角色(controller|node)/可选关联 DataSource/数据面状态/遥测通道 → 保存；重名拦截
3. 检查: 点 ✅ 刷新数据面状态；点 👁️ 看该集群独立遥测（事件列表 + 资产按类型汇总）
4. 新建升级: Edge 升级页「+ 新建升级任务」填目标版本/关联集群/策略(batch|all_at_once)/每批数量 → 创建(自动按在线 edge 会话生成 upgrade+verify 步骤)
5. 执行: 点 ▶️ → 任务走 pending→running→completed，进度到 100%，每 agent 的 upgrade/verify 全 success
6. 失败回滚: 让某 agent verify 失败（如先手动把某 agent_version 改成非目标值）→ 执行 → 该批 upgrade 自动 skipped(回滚) → 任务 failed/rolled_back
7. 暂停/续传: running 中点 ⏸ → paused；查询列表/详情可看步骤状态与日志（重启后端不丢，可续查）

### 通过标准
- [ ] 集群注册/列表/遥测/检查/编辑/删除全链路可用；数据面状态反映 DataSource 状态
- [ ] 每集群遥测通道独立，事件按 cluster 过滤正确
- [ ] 升级任务创建生成 step，run 后 completed+progress=100+全部 success
- [ ] verify 失败触发该批回滚、任务 failed；日志与步骤状态持久化（重启 backend 后仍可查）
- [ ] `k8s_clusters`/`k8s_upgrade_jobs`/`k8s_upgrade_steps` 表存在；菜单可见；`npm run build` 通过

## 2026-08-13: 网络设备管理(F6)

### 功能说明
- 纯 Python SNMP 客户端（v1/v2c GET/WALK，UDP）；设备管理 + SNMP 连通校验 + IF-MIB 接口轮询 + LLDP/CDP 邻居发现 + 主机-交换机端口链路映射。
- 开发/演示：设环境变量 `AIOPS_SNMP_MOCK=1`（或在项目根建 `snmp_mock.flag`）启用 mock 数据。

### 操作步骤
1. 入口: 系统配置 → 系统管理 → **网络设备**(`/network-devices`)
2. 添加设备: 「+ 添加设备」填设备名/IP/类型(交换机等)/SNMP 版本/community/端口 → 保存
3. 连通校验: 点 🔍 → ok 则自动标厂商型号；不可达标 error
4. 接口轮询: 点 📊 → 采集 N 个接口(名称/MAC/速度/up-down/流量计数)；详情页展示接口表
5. 邻居发现: 点 🕸️ → 发现 LLDP/CDP 邻居(本端接口/邻居设备/邻居端口)
6. 主机链路映射: 「🔗 主机链路映射」输入主机 IP → 反查其接入的交换机/端口（需先轮询交换机接口以采集端口 MAC）

### 通过标准
- [ ] 设备 CRUD 正常；重名/缺字段校验
- [ ] validate 返回 sysDescr/uptime/objectID，ok 后标厂商型号
- [ ] poll 落 `network_interfaces`（接口数>0、up 数正确）；detail 展示接口表
- [ ] discover 落 `network_neighbors`（LLDP 邻居≥1）
- [ ] map-links 按主机 MAC 反查交换机端口
- [ ] `network_devices/interfaces/neighbors` 表存在；菜单可见；`npm run build` 通过
