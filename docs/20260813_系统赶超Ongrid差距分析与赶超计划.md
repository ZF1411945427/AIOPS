## 一、项目定位差异(本质区别)

| 维度 | Ongrid | 本系统 (AIOps) |
|---|---|---|
| **本质** | **运维 AI Agent 平台**——Agent 是绝对主角,所有能力围绕"LLM Agent 自主排查+修复"构建 | **AIOps 中台**——功能覆盖面碾压,但 Agent 是"众多功能之一",非架构内核 |
| **定位口号** | "Ops AI Agent that finds root cause & fixes it, from Slack/Telegram" | "监控·告警·RCA·自动化·部署·SRE 一站式运维平台" |
| **技术栈** | Go 1.25 + React + Casbin + Eino(LLM 编排) + Qdrant + frontier 隧道 | Python FastAPI + Vue3 + SQLite + 自研调度 |
| **规模(后端)** | ~2000 行入口 + 有界上下文 DDD 分层 | 123 个 router + 79 个 service + 133 张表(~62,000 行) |
| **前端** | React 18 + TS + Tailwind + @xyflow(工作流画布) | Vue3 + Element Plus + ECharts + UniApp 移动端 |

**一句话**: 本系统像"功能大而全的庞然大物",Ongrid 像"小而精的 Agent 引擎"。**本系统功能广度远超 Ongrid,但 Ongrid 的 Agent 内核深度、工程化架构、可部署性远超本系统。**

## 二、功能层面:本系统有而 Ongrid 没有(优势项)

这些本系统**已经超越** Ongrid,不是差距,但列出以完整对比:

1. **AI 自动部署引擎(最大亮点)**: `deploy_service.py`(3646 行)的 L4/L5 自主执行——AI 解析 SOP → 自动推断环境变量 → 自主生成命令 → fix/retry/skip/rollback 决策 → 健康门控 → 特征学习。Ongrid **没有**应用部署能力(IaC 只管 K8s 升级,不部署 docker compose)。

4. **CMDB 资产发现/生命周期/外部 CMDB 集成**: Ongrid 的 device 是轻量的(fingerprint),无完整资产生命周期。
5. **内置指标采集(SSH 采集 21+ 指标)**: Ongrid 的指标必须依赖外接 Prometheus。
6. **移动端 UniApp(19 页)**: Ongrid 无移动端。
7. **License 授权、双库(demo/real)切换、背景任务看板**: Ongrid 无。

### 2. 工作流 DAG 引擎(可视化编排)—— 修正:骨架已达标,差在自动化触发与调度

> **⛔ 修正说明(2026-08-13 复查)**: 初版报告误判"本系统工作流是审批式模板串行、无 DAG 画布"。**实际代码层复核(`agent_workflow_service.py` + `AgentWorkflowEditor.vue` + VueFlow)发现本系统已具备一套完整的 Coze 风格 DAG 引擎 + 可视化画布**,不是空白。真实差距集中在"自动化触发与并行调度"两个维度(见下)。

**本系统已有能力(非差距)**:
- **8 种节点执行器**: start / end / llm / knowledge / tool / condition / code / http(`agent_workflow_service.py` 的 `NODE_EXECUTORS`)
- **确定性 DAG 执行**: `topological_sort()` + 依赖判定 + 条件分支路由(condition 节点的 matched_branch 路由到对应分支)
- **可视化画布**: 前端 `AgentWorkflowEditor.vue` 用 **VueFlow**(真画布: 拖拽/连线/minimap/controls),非纯表单
- **变量传递**: Jinja2 渲染 `{{ nodes.xxx.output }}`
- **执行控制**: 人工确认节点(PendingAction 暂停)、retry / abort / confirm / cancel
- **审计**: `WorkflowAuditLog`(不可抵赖)
- **5 个预置模板**(智能告警根因分析、智能运维问答等),含发布/草稿管理

**真实差距(需补齐)**:

| 能力 | Ongrid flow | 本系统 |
|---|---|---|
| **trigger 触发器** | 3 种: manual / **alert(告警)** / **cron(定时)** | 有 `trigger_type` 字段(manual/alert_auto),但**执行入口只有 API 手动触发**(`agent_workflow.py` 仅 `start_workflow_run(trigger_source="api")`),`alert_auto` 只是存字符串、**无任何后台接线 → 不生效** |
| **cron 定时调度** | robfig/cron,30s tick 调度器 | **完全没有** cron 调度器 |
| **并行 fan-out** | 确定性 fan-out(并发上限可配),OR-join + execute-once + error port 区分输出 | `_advance_run()` **单线程串行推进**(后台 thread 每轮扫依赖,同一时刻只跑一个节点),多分支被串行化 |
| **调度可恢复性** | job 队列 + 状态机 | 执行线程 `threading.Thread(daemon=True)`,**进程重启 → 未完成 run 直接丢失**,无 job 恢复 |
| **引擎纯净性(seam)** | 引擎**绝不调 LLM**,agent/llm/tool/notify 通过 seam 注入,引擎确定性 | `_exec_llm` 直接在引擎里调 `call_llm`,**无 seam 抽象**,非确定性埋在引擎,难测试/难确定性重放 |
| **notify 通知节点** | ✅ action-notify | ❌ 无(工作流内不能发飞书/钉钉/企微通知) |
| **agent 子代理节点** | ✅ agent 类型节点(可嵌子代理) | ❌ 无(不能把某子代理当节点嵌入) |
| **表达式引擎** | `{{trigger.*}}` 统一数据流 | Jinja2 + `_eval_condition`(contains/eq/ne/gt/lt/in/startswith),够用但无逻辑组合语法糖 |

**结论**: 本系统智能体编排**骨架已达标(DAG+画布),差距在"自动化触发(告警/cron)与并行调度"这一让工作流从'手动手册'变'自动闭环'的关键能力**——而这正是 Ongrid flow 的灵魂。
