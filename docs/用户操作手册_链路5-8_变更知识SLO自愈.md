# 链路5：事件变更关联故障

## 说明
⚠️ **链路5 当前实现**：变更记录仅作为 RCA 分析的辅助证据，**不会自动触发故障单**。
- 变更记录写入 `AssetChangeLog` 表（资产更新/健康扫描时自动记录）
- RCA 分析时查询关联资产的变更记录，作为时间线事件
- **无** `ChangeRecord` 模型，**无**变更直接触发故障的自动化链路
- 实际模型为 `ChangeRequest` + `ChangeTask`

## 第一步：记录资产变更

### 操作页面
**侧边栏** → **可靠性工程** → **SLO 管理**（Tab 容器，含「SLO 配置 / SLO 仪表盘 / 错误预算 / 预算消耗 / 可用性报表」五个 Tab）

> 说明：本手册链路7 起，「错误预算 / 预算消耗 / 可用性报表」等 SLO 结果查看已于 SLO 管理页内以 Tab 呈现，不再各自独立为菜单。


### 操作步骤

1. **新建 SLO**
   - 点击「新建 SLO」按钮
   - **SLO 名称**：输入 `API 可用性 SLO`
   - **关联服务**：选择目标资产（如 API 网关）
   - **SLO 目标**：输入 `99.9`（可用性 99.9%）
   - **时间窗口**：选择「滚动 28 天」
   - **Error Budget**：自动计算 `(1 - 0.999) * 总请求数`

2. **保存 SLO**
   - 点击「保存」
   - SLO 配置出现在列表中，状态为 `未计算`

## 第二步：查看 SLO 状态与计算结果

### 操作页面
**侧边栏** → **可靠性工程** → **SLO 管理** → **SLO 配置** Tab

> 说明：SLO 管理为一页多 Tab 容器。状态在「SLO 配置」Tab 实时展示；「SLO 仪表盘 / 错误预算 / 预算消耗 / 可用性报表」Tab 用于 SLO 结果的深入可视化。

### 操作步骤

1. **查看 SLO 列表与状态**
   - 「SLO 配置」页以表格展示每个 SLO：服务名、目标可用性、窗口(天)、总请求、错误请求、状态
   - 状态徽章：`healthy`（绿色）/ `warning`（橙色）/ `critical`（红色）
   - 状态由后台基于「错误消耗 vs 窗口期长度」自动计算并更新

2. **触发/刷新 SLO 计算（后台自动）**
   - 系统调用 `POST /api/sre/slo/calculate`，后台执行 `slo_service.calculate_all_slo()`：
     - 查询 `SLOConfig` 表中所有 SLO
     - 对每个 SLO，从 VictoriaMetrics 查询实际指标
     - 计算可用性 = 成功请求数 / 总请求数
     - 计算 Error Budget = (1 - SLO目标) * 总请求数 - 失败请求数
     - 计算 Burn Rate = Error Budget 消耗量 / 时间窗口长度
     - 更新 `SLOConfig.status`：
       - Burn Rate > 10 或 Budget < 20% → `critical`
       - Burn Rate > 5 或 Budget < 50% → `warning`
       - 其他 → `healthy`
   - 页面刷新，显示最新计算结果

3. **查看 SLO 详情**
   - 在「错误预算」Tab 查看各 SLO 的错误预算消耗与剩余
   - 在「预算消耗」Tab 查看燃烧速率（Burn Rate）变化
   - 在「可用性报表」Tab 查看历史可用性趋势

### 看到什么
- SLO 配置列表显示每个 SLO 的状态徽章（healthy/warning/critical）
- SLO 管理页各 Tab 显示：配置列表状态徽章、仪表盘、错误预算消耗/剩余、燃烧速率、可用性报表历史趋势

### 结果
SLO 计算完成，展示当前可用性和 Error Budget 状态。

# 链路8：告警直接触发自动响应

## 说明
✅ **链路8 完整实现**：告警 → 规则匹配 → SSH 远程执行 → 效果追踪，形成完整闭环。

## 第一步：配置自动响应规则

### 操作页面
**侧边栏** → **运维工作台** → **自愈管理** → **自愈规则**

> 说明：自愈规则配置在「自愈规则」页，该页含「AI 自愈工作台 / 简单规则 / 执行记录」三个 Tab（执行记录即自愈执行历史）。

### 操作步骤

1. **查看现有规则**
   - 页面显示已配置的自动响应规则列表
   - 每条规则显示：
     - **规则名称**
     - **关联告警规则**：匹配的 `AlertRule`
     - **动作类型**：restart / clean / run_command / notify
     - **状态**：启用 / 禁用

2. **新建自动响应规则**
   - 点击「新建规则」按钮
   - **规则名称**：输入 `CPU过高自动重启`
   - **关联告警规则**：下拉选择 `CPU使用率过高` 规则
   - **动作类型**：选择 `restart`
   - **服务名称**：输入 `nginx`（systemctl restart 的服务名）
   - **启用状态**：开启
   - 点击「保存」

### 看到什么
- 规则列表显示新创建的规则
- 规则状态为「已启用」

## 第二步：告警触发自动响应（后台自动）

### 说明
自动响应是**后台定时任务**，无需手动操作。

### 执行过程

1. **定时扫描**：后台任务 `remediation_service.check_and_remediate()` 每轮循环执行
2. **规则匹配**：查询 `AutoRemediation` 表中 `enabled=True` 的规则
3. **告警关联**：对每条规则，查询 `status=triggered` 的关联告警
4. **去重检查**：同一告警+同一规则最近已执行过则跳过
5. **SSH 执行**：
   - 根据 `alert.asset_id` 查 `Asset` 获取 IP/SSH 凭据
   - 用 paramiko SSH 连接远程资产
   - 按 `action_type` 执行动作：
     - `restart`：`sudo systemctl restart {service}`
     - `clean`：`find {path} -type f -mtime +7 -delete`
     - `run_command`：执行自定义命令（危险命令黑名单拦截）
     - `notify`：发送通知
6. **写入执行日志**：创建 `RemediationLog` 记录（成功/失败/输出）
7. **更新告警状态**：`Alert.status = acknowledged`
8. **效果追踪**：30 分钟后检查告警是否恢复，写入 `RemediationEffectRecord`

### 看到什么
- 无需手动查看
- 执行结果在「运维工作台」→「自愈管理」→「自愈规则」的「执行记录」Tab 中查看

## 链路8 补充：自愈工作流

### 操作页面
**侧边栏** → **运维工作台** → **自愈管理** → **自愈工作流**

### 操作步骤

1. **新建/编辑工作流**
   - 填名称 + 关联规则 ID + 步骤编排（healthcheck / restart / clean / scale / notify / run_command）
   - 可增删 / 上下移步骤 → POST `/remediation-workflows/api/create`、`/{id}/update`

2. **运行 / 模拟**
   - 运行（dry_run=false）→ 真实执行
   - 模拟（dry_run=true）→ 预览不落地 → POST `/remediation-workflows/api/{id}/run`

3. **启用/禁用 / 删除**
   - toggle 开关启停；删除工作流

4. **查看自愈日志**
   - 自愈日志表格（分页）→ GET `/remediation-workflows/api/logs`

### 看到什么
- 工作流卡片（动作步骤链）+ 自愈日志表格 + 可视化步骤编排器 + 模拟结果弹窗

## 常见问题

### Q1：SLO 计算结果不准确？
- **检查**：VictoriaMetrics 是否有对应的指标数据
- **检查**：SLO 配置的时间窗口是否正确
- **检查**：`slo_service.calculate_all_slo()` 是否在后台循环中执行

### Q2：自动响应没有执行？
- **检查**：`AutoRemediation` 是否 `enabled=True`
- **检查**：关联的 `AlertRule` 是否匹配当前告警
- **检查**：`RemediationLog` 是否有最近执行记录（去重机制会跳过）
- **检查**：SSH 凭据是否正确（`Asset.connection_config`）

### Q3：自动响应执行失败？
- **检查**：网络是否连通（能否 SSH 到目标资产）
- **检查**：服务名是否正确（`systemctl restart {service}`）
- **检查**：命令是否被危险命令黑名单拦截

### Q4：效果追踪显示未恢复？
- **检查**：告警是否在 30 分钟内解决
- **检查**：自愈执行是否成功（检查 `RemediationLog.success`）
- **检查**：指标是否恢复正常（检查 `MetricRecord` 最新值）

## 专业术语

| 术语 | 英文 | 说明 |
|------|------|------|
| Change Correlation | 变更关联 | 将基础设施变更事件与故障事件时间线对齐 |
| RCA | Root Cause Analysis | 根因分析，定位故障根本原因 |
| Investigation Package | 调查包 | 结构化 RCA 输出（Facts/Timeline/Candidates/Evidence/Exclusions/NextSteps） |
| SLO | Service Level Objective | 服务级别目标，定义可用性/延迟等指标目标值 |
| Error Budget | 错误预算 | SLO 允许的容错空间 |
| Burn Rate | 燃烧速率 | Error Budget 消耗速率，>1 表示正在消耗预算 |
| Auto-Remediation | 自动修复 | 根据预定义规则自动执行恢复操作 |
| Steady-State | 稳态 | 系统正常运行时的状态基线 |
